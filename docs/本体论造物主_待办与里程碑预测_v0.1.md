# 本体论造物主：待办、论证与里程碑预测 v0.1

> 状态：提案（2026-09-21）  
> 关联：[Issue #25：仪式圣典](https://gitea.capitaltrain.cn/seekkey/kunpengzhi-altar/issues/25)、[Issue #26：本体论造物主内核](https://gitea.capitaltrain.cn/seekkey/kunpengzhi-altar/issues/26)

## 0. 决策

本项目的交付物不只是一个祭坛网页。祭坛是第一个可运行场景；长期资产是一套可审计、可组合、可在不同观察时空中复用的世界模型库。

因此采用下列单向结构：

```text
World Kernel（对象、关系、时空、推演、不变量）
        ↓
Admission / Provenance（准入、版本、证据与设定边界）
        ↓
Scenario Manifest（选择对象 + 声明观察事件 + 声明装配）
        ↓
Adapters（Three.js / audio / UI / storage / network）
        ↓
祭坛仪式、巴纳德观察者、未来场景
```

依赖只允许向下。渲染、浏览器、交互和故事页面不得反向定义世界事实；场景不得把业务规则偷偷写入对象内部。

## 1. 为什么顺序不能颠倒

### 1.1 先定义对象，才能谈复用

当前的 `AltarScene` 同时拥有 WebGL、DOM、输入、角色、时间轴、音频、叙事、几何、资产和销毁。继续从它抽取“通用组件”，只会把祭坛的隐性假设复制到下一个场景。

先定义独立对象及其契约，才能让“巴纳德星”“观察者”“49 节点”“仪式分数”等对象不认识自己被哪个页面使用；场景只负责选择和连线。

### 1.2 先定义认识论类型，才能阻止叙事污染数据

同一概念会同时出现在观测、模型、推论、设定和演出中。没有类型与合法转换规则，`[设]` 会在视觉或文案中静默伪装成 `[史]`，下游每次引用又都必须重审来源。

对象在准入时携带 `[史] / [模] / [推] / [设] / [演] / [工]`、前提、用途边界和 provenance；之后调用方只检查接口是否兼容。这是质量保险的前提，而不是写完后补标签。

### 1.3 先统一时空契约，才能让“换场景”真的只是换观察事件

一个可复现场景必须声明：坐标时间、位置、四维速度/参考系、朝向、单位、尺度、精度预算。没有这些，所谓“巴纳德观察者”只能是动画，无法审计；不同场景也会各自发明坐标、时间和尺度。

### 1.4 先有纯内核与确定性测试，才能相信三维结果

Three.js 画面是 adapter 的结果，不是事实源。若模型只能在浏览器、单例音频或一段动画循环里运行，就无法在 Node、CI、别人的工程或未来的渲染器中复算。必须先让核心在无头环境确定性运行，再把它交给视觉层显影。

### 1.5 第二场景是复用的最低证明

只迁移祭坛不能证明架构成功，因为所有假设仍可能恰好适配祭坛。必须使用同一批 kernel 对象装配一个最小的“巴纳德观察者”审计场景：它不需要先做成完整作品，但必须能给出观察事件、光锥/参考系与可追溯输出。只有这样，库才不是换名字的祭坛代码。

## 2. 不可变质量契约

每个可引用世界对象必须具备：

| 契约 | 含义 |
| --- | --- |
| `id + semanticVersion` | 稳定身份与兼容性判断 |
| `epistemicKind` | `[史]/[模]/[推]/[设]/[演]/[工]`，不可省略 |
| `claims / nonClaims` | 明说其断言与不作断言的边界 |
| `assumptions / dependencies` | 前提与所依赖对象的锁定版本 |
| `units / frame / domain` | 单位、参考系、适用时空域与精度 |
| `invariants / failureModes` | 必须保持的性质、失败与不确定性 |
| `permittedUses / forbiddenUses` | 能用于何种演出、推演或界面；禁止何种越界使用 |
| `provenance` | 数据、文献、模型、正典或人工裁决的来源链 |

下游场景不重新阅读每个对象的内部实现；它只验证：对象版本、认识论类型、输入前提、时空域、许可用途与 adapter 能力是否匹配。若接口不足以回答这些问题，说明对象尚未通过准入。

## 3. 工作分解与依赖

### M0 — 架构考古与冻结边界

**目的：** 先知道哪些现有行为、数据和隐性耦合必须保留或迁移，避免“重构”成为悄悄改写正典。

- [ ] 输出现有导入图、全局单例、DOM/Three/Tone 依赖、时间源和共享可变状态清单。
- [ ] 标出 `AltarScene` 对世界事实、场景装配、adapter 生命周期三类职责的每一处归属。
- [ ] 为现有 30 分钟仪式建立可重复的 golden evidence（关键时码状态、音频包络、镜头/节点输出）。
- [ ] 冻结迁移期的公共行为契约；任何有意变化必须有对应 Issue 与证据。

**完成证据：** 一份依赖图、一个迁移映射表、可在 CI 重跑的黄金样本。

**为什么先做：** 没有基线，后续“解耦”无法证明未把规则或失败条件删掉。

### M1 — 最小 World Kernel 与类型系统

**目的：** 建立不依赖场景的本体语言。

- [ ] 新建纯 TypeScript kernel 包；静态门禁禁止 import Three.js、React、DOM、Tone、网络、存储和单例。
- [ ] 定义 `WorldObject`、`Relation`、`SpacetimeEvent`、`ReferenceFrame`、`Quantity`、`Uncertainty`、`Provenance` 的最小契约。
- [ ] 定义认识论类型与合法转换；非法的 `[设] → [史]`、无来源 `[推]`、单位/参考系不明等组合必须被拒绝。
- [ ] 定义对象序列化、稳定 ID、语义版本与兼容策略。

**完成证据：** Node 单测可创建、序列化、验证和拒绝非法对象；依赖门禁可证明 kernel 无运行时污染。

**依赖：** M0。

### M2 — 准入、版本与可追溯图

**目的：** 把“质量保险”变成机器可验证的前置条件。

- [ ] 定义 admission manifest 与 schema；对象未声明来源、前提、时空域、不变量或用途边界时不可发布。
- [ ] 构建依赖图、版本锁与冲突报告；循环依赖、认识论越级、单位不匹配必须可定位。
- [ ] 为 `[史]`、`[模]`、`[设]` 各建立最小准入样例；将《天权记》《牧月记》的关系仅作为正典引用样例，不提升为事实输入。
- [ ] 导出人可读的“为何可用／为何不可用”审计报告。

**完成证据：** 一个对象包可以被独立验收；一个故意越界的组合在 CI 中失败并报告完整路径。

**依赖：** M1。

### M3 — Scenario Manifest 与装配器

**目的：** 使场景成为声明，而非第二个世界内核。

- [ ] 定义 `ScenarioManifest`：对象选择、固定版本、观察事件、精度预算、激活关系、允许 adapter 和输出声明。
- [ ] 定义纯装配器：输入 manifest，输出世界状态/派生状态；不得生成 DOM、音频或 WebGL 对象。
- [ ] 建立“祭坛仪式”最小 manifest，抽离目前散落在 `types/altar.ts`、`data/*` 与 `AltarScene` 的时间/世界规则。
- [ ] 固定 public、director、engineering 的差异为场景/adapter 权限声明，而不是把角色逻辑混入世界对象。

**完成证据：** 同一个 manifest 在 Node 与浏览器中产生相同的核心快照；改一个观察事件不会改写对象自身。

**依赖：** M1、M2。

### M4 — Adapter Ports 与祭坛迁移

**目的：** 让 Three.js 成为可替换的显影层。

- [ ] 定义 render、audio、input、persistence、network 的 port；所有副作用只从 port 发生。
- [ ] 将 Three.js Builder/Rig 改为读取装配结果的 renderer adapter，不再作为事实、时间或权限的权威来源。
- [ ] 去除或封装 `altarAudio` 等全局单例，使其生命周期由 scenario host 控制。
- [ ] 将 `AltarScene` 收敛为 host/composition root；它只能创建 adapter、装配 manifest、调度帧与释放资源。
- [ ] 用 M0 黄金样本证明视觉/音频行为没有无意回归。

**完成证据：** 祭坛可由 manifest 启动；无头 adapter 能跑完整 1800 秒；旧的场景总管不再拥有世界规则。

**依赖：** M3。

### M5 — 第二场景：巴纳德观察者审计原型

**目的：** 验证复用，不先追求完整视觉作品。

- [ ] 声明一个观察事件：时间、位置、速度、参考系、朝向与精度预算。
- [ ] 将天体目录/星历、传播假设、相对论视觉变换分别以 `[史]`、`[模]` 对象准入；虫洞仅可作为 `[设]` 的场景入口。
- [ ] 实现无渲染的延迟光锥、方向、频移/光行差输出，并给出不确定性与模型限制。
- [ ] 以同一 kernel 对象接入一个最小 Three.js 审计视图；显示“观礼”与“审计”两种 adapter 输出。

**完成证据：** 从相同版本锁的对象图，能复算一个观察快照；切换观察事件会得到不同结果，且来源与假设可追溯。

**依赖：** M2、M3、M4。

### M6 — 组合门禁、发布候选与复用准入

**目的：** 把可靠性从一次性交付变为发布制度。

- [ ] CI 分层门禁：类型/单位/来源、确定性、组合兼容性、adapter 契约、黄金快照、性能预算。
- [ ] 发布物生成 SBOM 式对象清单、manifest lock、依赖图与证据包。
- [ ] 建立破坏性变更策略：对象接口不兼容时必须升主版本；场景 manifest 不得静默漂移。
- [ ] 对外提供最小复用指南与示例，证明第三方无需打开对象内部实现即可合法装配。

**完成证据：** 一个干净环境可以锁定版本复跑祭坛与巴纳德观察者；外部调用者仅凭契约完成一次受限装配；所有门禁通过。

**依赖：** M4、M5。

## 4. Milestone forecast

以下是 **一名有效工程师、既有行为冻结、数据源许可明确、审查不长期阻塞** 前提下的工作量预测；它不是日历承诺。若同时推进公共 30 分钟仪式的内容生产，应将其视为独立并行流，不能挤占 kernel 的验收时间。

| 里程碑 | 预测有效工日 | 累计 | 可交付状态 |
| --- | ---: | ---: | --- |
| M0 架构考古与基线 | 3–5 | 3–5 | 知道现有系统的真实边界，能防回归 |
| M1 最小 kernel | 5–8 | 8–13 | 有独立的世界对象与时空类型 |
| M2 准入与追溯 | 5–8 | 13–21 | 对象可前置验收，质量开始可继承 |
| M3 场景装配 | 4–6 | 17–27 | 场景与世界事实首次真正分离 |
| M4 祭坛迁移 | 8–12 | 25–39 | 可称为“可靠祭坛 Alpha” |
| M5 巴纳德观察者 | 8–15 | 33–54 | 证明库能跨场景复用 |
| M6 发布候选 | 5–8 | 38–62 | 可称为“可复用世界库 v1.0” |

以连续投入估算，M4 约为 5–8 周；M6 约为 8–13 周。影响区间最大的不是渲染，而是三个未知：现有规则迁移时发现的隐性耦合、外部天体数据与模型的准入深度、以及质量审查对语义版本和证据边界的裁决速度。

## 5. 开工顺序与停止条件

第一张实施工单必须从 M0 开始，而不是直接建巴纳德视觉或继续拆 `AltarScene`。

每一阶段只有在其完成证据被复核后才能进入下一阶段；特别是：

- M1 未通过前，禁止向场景层新增“通用世界对象”；
- M2 未通过前，禁止将正典设定接入事实/模型输入；
- M3 未通过前，禁止宣布“不同场景只换时空”；
- M5 未通过前，禁止宣布本库已被跨场景复用证明；
- M6 未通过前，不向第三方承诺接口稳定性。

这不是延缓创作，而是避免把一个极具说服力的世界观建立在不可审计、不可替换、不可复算的积木上。
